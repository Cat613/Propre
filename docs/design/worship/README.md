# 예배 운영 기능 상세 설계

작성: 2026-10-16 Asia/Seoul · 상태: 상세 설계 v1 · WSP-P0~P5b 로컬 구현·검증·UI 검토 완료

사용자가 요청한 7개 기능의 설계 기준점이다. 기능별 정책은 각 상세 문서에서, 공통 저장·송출·권한은 [공통 계약](예배-운영-기능-공통-계약.md)에서 관리한다. 사용자는 상세 설계 완료와 앱 자동 업데이트 세션의 개발 완료를 선행 조건으로 7개 기능의 순차 구현·검증을 승인했다. 현재 7개 기능의 로컬 구현·검증·UI 검토를 마쳤으며 구현 착수 조건과 진행 상태는 [개발 계획](../../delivery/예배-운영-기능-순차-개발-계획.md)에 기록한다. 기존 기능의 동작은 기존 구현 문서가 기준이다.

## 설계 원칙

1. 예배 순서 선택, 자료 편집, 실제 송출을 분리한다. 큐시트 이동만으로 화면·소리가 바뀌지 않는다.
2. 전체 큐시트를 순서의 기준으로 삼고, 기존 곡 목록은 곡 항목의 투영으로 유지한다.
3. 예배별 곡 사본 정책을 유지한다. 템플릿·원곡 수정이 과거 예배에 전파되지 않는다.
4. 운영자 메모·무대 안내를 청중용 message 레이어와 공유하지 않는다.
5. 기본 운영은 오프라인으로 가능하다. 웹 접근과 실제 장비의 동작은 별도 확인한다.
6. 빈 상태, 취소, 충돌, 저장 실패, 창 재연결, 재시작을 각 기능의 정상 흐름에 포함한다.

## 상태·식별자·변경 관리

이 묶음은 전역 REQ/TASK/TC/ADR 번호 충돌을 피하기 위해 독립된 `WSP-01`~`WSP-07` 네임스페이스를 사용한다. 테스트는 `WSP-T01`~`WSP-T07`, 단계는 `WSP-P0`~`WSP-P5`, 결정은 공통 계약의 `WSP-D01`~`WSP-D06`으로 연결한다. 구현 착수 시 기존 요구사항·백로그·결정 문서에 매핑하고 이 문서에 링크를 추가한다. 기존 번호를 재사용하지 않는다.

설계 상태는 `제안 → 확정 → 구현 중 → 구현됨 → 수용 확인`으로 관리한다. 현재 WSP-01은 **로컬 수용 확인**, WSP-02는 **로컬 수용 확인**, WSP-03은 **로컬 수용 확인**, WSP-04는 **로컬 수용 확인**, WSP-05는 **로컬 수용 확인**, WSP-06은 **로컬 수용 확인**, WSP-07은 **로컬 수용 확인**이다. 기능 완료 표시는 실행 증거와 미검증 범위를 연결한 뒤 변경한다. 제품/개발/QA 책임은 역할 제안이며 실제 담당자와 출시일은 미정이다.

변경 시 기능 문서의 정책·공통 계약·테스트·개발 계획을 함께 갱신하고 아래 이력에 변경 이유를 남긴다. 구현과 달라지면 현재 동작과 목표 동작을 구분한다. 중복된 상태 표를 여러 문서에서 수동 관리하지 않고 이 문서를 상태 기준점으로 삼는다.

## 초기 결정과 사용자 확인이 필요한 항목

| 항목 | 설계 기본값 | 후속 확인 시점 |
| --- | --- | --- |
| 순서 진행 | 운영자가 수동 실행, 자동 다음 순서 없음 | WSP-01 운영자 리허설 |
| 시간 | 자동 타이머 시작 기본 꺼짐, 청중 표시 없음 | WSP-05 실제 장시간/운영자 리허설 |
| 공유 | 로컬 PDF·인쇄, 전송은 운영자가 수행 | WSP-07 수용 확인 |
| 템플릿 | 자동 반복 생성 없음, 새 예배는 독립 사본 | WSP-06 수용 확인 |
| 무대 메시지 | 20초, 단일 활성 안내, 청중 노출 없음 | 실제 Stage 가독성 평가 |

이 기본값으로 구현 계획을 구체화할 수 있다. 교회별 예배 시간·메모·담당자·브랜드는 합성 예시로만 작성하며 실제 개인정보를 설계나 로그에 넣지 않는다.
