기존 테스트는 모두 통과했지만, 기존 검사에 없던 조작 조합에서 결함 4건을 재현했다. P1은 의도하지 않은 송출 변경 가능성이 있어 우선 수정할 항목, P2는 조작 대상 혼동 또는 입력 방식 누락이다.

## 확인된 결함

### R1 · P1 · 버튼의 Space 조작이 슬라이드를 송출한다

- 재현: 콘티 첫 곡 선택 → 슬라이드는 대기 상태로 유지 → `콘티 더 보기` 버튼으로 포커스 이동 → Space.
- 실제: 메뉴를 여는 키 입력이 전역 송출 단축키로 처리되어 첫 슬라이드가 활성화된다. 격리 Electron 검사에서 슬라이드의 `data-live=true`까지 확인했다.
- 원인: [전역 단축키](../../src/hooks/useHotkeys.ts)의 Space/화살표 처리 앞에서 버튼·summary·역할 기반 조작 요소의 키 소유권을 구분하지 않는다. [차단 조건](../../src/hooks/useModalGuard.ts)은 입력·select·모달 중심이다.
- 개선: 폼·버튼·summary·ARIA 조작 요소가 사용하는 키는 해당 요소에 맡기고, 슬라이드 이동 단축키를 실행할 수 있는 영역과 명령을 구분한다. `event.defaultPrevented`도 존중한다. F2 긴급 중지 경로는 유지한다.
- 완료 기준: 더 보기·오디오 재생·자료 선택 버튼의 Space 조작이 해당 기능만 실행하며 현재 송출을 바꾸지 않는다. 슬라이드 영역의 Space/화살표와 F2는 정상 동작한다.

### R2 · P1 · PDF 준비 중 페이지 변경 시 이전 준비 결과가 다시 활성화된다

- 재현: 2페이지 PDF의 1페이지 `화면 준비` 실행 → 준비 응답이 돌아오기 전에 페이지 입력을 2로 변경 → 준비 완료 → `준비 화면 송출`.
- 실제: 입력칸은 2, 미리보기는 1페이지이고 송출 버튼이 활성화된다. 송출 결과는 1페이지다. 렌더 완료 후 IPC 응답에 600ms 지연을 넣어 이 순서를 결정적으로 재현했다. 사용자 데이터나 외부 문서는 사용하지 않았다.
- 원인: [페이지 입력](../../src/components/OutputResourcesPanel.tsx)의 변경은 `setPrepared(null)`만 수행한다. 진행 중 준비 요청 번호를 무효화하지 않아 이전 응답이 다시 prepared를 채운다. `ready` 조건도 자료 ID·generation만 확인하며 페이지·회전을 대조하지 않는다.
- 개선: 페이지·회전·자료 revision 변경마다 준비 요청을 무효화하고, 준비 결과의 자료·revision·페이지·회전·generation이 현재 선택과 모두 일치할 때만 송출을 허용한다. 준비 중 입력을 잠그는 것은 보조 수단으로 사용한다.
- 완료 기준: 응답이 늦는 동안 페이지를 바꾸면 이전 결과는 송출 불가 상태가 되고, 현재 입력에 맞는 새 준비 후에만 송출할 수 있다. 자료 전환·패널 닫기·중지의 기존 취소 보호도 유지한다.

### R3 · P2 · 자료 선택과 주소 수정 대상이 어긋난다

- 재현: 웹 자료 A 선택 → `주소 수정` → 자료 B 선택 → 열려 있는 폼에서 이름 수정·저장.
- 실제: 준비 패널은 B지만 수정 폼은 A로 유지되며 저장은 A를 바꾼다. 화면의 준비 대상과 저장 대상이 다르다. 격리 검사에서 저장 뒤 A의 이름 변경과 B의 이름 유지를 확인했다.
- 원인: [자료 선택 처리](../../src/components/OutputResourcesPanel.tsx)의 `choose()`가 `editing`·폼 값을 정리하거나 수정 대상 안내를 갱신하지 않는다. 제출은 기존 `editing.id`를 사용한다.
- 개선: 다른 자료 선택 시 수정 폼을 닫거나 새 자료에 맞춰 전환한다. 수정 중인 대상 이름을 폼 제목에 표시한다. 변경한 입력이 있다면 전환 시 보존 또는 취소 정책도 명확히 정한다.
- 완료 기준: 선택 자료와 수정 대상이 다르면 조용히 이전 자료를 저장하지 않는다. A/B 전환·새 주소 추가·패널 닫기·저장 실패 재시도를 함께 검사한다.

### R4 · P2 · 콘티 행에 키보드 포커스는 가지만 선택·이동이 연결되지 않는다

- 재현: 첫 곡을 연 뒤 두 번째 곡 행으로 포커스 이동 → Enter.
- 실제: 두 번째 곡이 열리지 않고 첫 곡의 슬라이드가 유지된다. 포인터로는 선택된다.
- 원인: [행 컴포넌트](../../src/components/SortablePlaylistItem.tsx)는 클릭만 선택에 연결한다. [콘티 패널](../../src/components/PlaylistPanel.tsx)의 정렬 sensor도 PointerSensor만 등록되어 있다.
- 개선: 곡 선택과 순서 이동의 키 조작을 구분한다. Enter로 곡 선택, 명시적인 키보드 이동 명령 또는 별도 정렬 모드를 제공한다. 제거 버튼의 포커스·이벤트 전파와 겹치지 않게 처리한다.
- 완료 기준: Tab/Enter만으로 곡을 열고 제거할 수 있으며, 순서 이동 역시 키보드로 가능하다. 곡 선택 자체는 라이브 송출을 변경하지 않는다.

## 추가 개선 제안 — 결함 재현과 구분

### I1 · 삭제 복구 경험 통일

웹·PDF와 콘티에는 복원 경로가 있지만 찬양 목록 삭제는 Repository.delete에서 항목을 제거하고, 이미지·영상·오디오 목록 삭제에도 전용 되돌리기 버튼이 없다. 슬라이드 Undo는 이 삭제를 복원하지 않는다. 미디어 원본 파일을 즉시 물리 삭제한다는 뜻은 아니다.

찬양·미디어 목록에도 휴지통/복원을 제공하고, `콘티에서 제거`, `찬양 목록에서 삭제`, `파일 정리`의 범위를 구분하는 것이 좋다. 기존 콘티의 독립 사본과 사용 중 미디어 보호를 유지해야 한다.

### I2 · PDF 페이지 입력 검증

페이지 입력은 min/max를 표시하지만 onChange는 빈 값→0, 소수, 전체 페이지보다 큰 값도 상태로 받는다. 서버 schema가 잘못된 준비를 거절하므로 이 항목을 잘못된 페이지의 정상 송출로 단정하지 않는다. 다만 페이지 범위 오류가 IPC 오류로 올라오기 전에 입력 옆에서 안내하고, 유효한 정수일 때만 준비 버튼을 활성화하는 것이 자연스럽다.

### I3 · 오디오 전환 정책과 상태 표시

`웹 소리 켜기`는 당시의 로컬 오디오를 일시정지하지만, 이후 오디오 플레이어 재생이나 미디어의 오디오 선택 경로는 웹 음소거 상태를 조정하지 않는다. 두 소스를 동시에 재생할 수 있는 구조다. 실제 스피커 혼음·음량은 이번에 시험하지 않았다.

동시 재생이 의도된 기능인지 정책을 정하고, 단일 재생 정책이면 재생 시작 경로를 통합한다. 동시 재생을 허용한다면 웹 소리와 로컬 오디오 각각의 재생 상태·중지를 한눈에 보여주는 편이 운영 실수를 줄인다.
