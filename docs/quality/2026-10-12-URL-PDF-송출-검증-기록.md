## 기준과 보호

기준 HEAD는 개발 시작 시 manifest(`/tmp/propre-output-implementation-baseline.json`)에 기록했다. develop의 로컬 소스에 구현하며 기존 설계 문서·생성 Electron 번들의 dirty 변경은 보존했다. 기능 검사는 합성 HTTP 페이지와 생성 PDF를 사용하고 비패키지 Electron 검사에서 실제 app.getPath('userData')가 임시 PROPRE_TEST_USER_DATA와 같은지 검사한다. 실제 사용자 자료로 기능을 송출·분석하지 않았다. 추가 패키지 실행의 격리 실패와 복구는 아래 별도 기록한다.

Electron 44.5.1 / macOS의 개발 환경이다. 기술 검증에서 단일 WebContentsView의 창 이동 후 renderer ID·입력값·쿠키·scroll 보존과 숨긴 창 capture를 확인했다. remote renderer는 앱 브릿지와 Node require가 없다.

새 단위 검사 5개는 URL 계약·v2 원본 보존·PDF 원자 등록/백업·잘못된 파일 거절·검증 실패 재연결 보호를 확인한다. 새 Electron 기술 검사 1개와 기능 검사 9개는 view 이동 상태, 준비/송출·Stage·재시작·화면 폭, 권한 격리/업로드 거절, 이동 뒤 오래된 토큰 거절, PDF 재연결 캐시 변경, renderer 중단 뒤 정지 화면/복귀와 컨트롤 창이 없는 상태의 정상 종료를 확인한다. 기존 오디오·슬라이드·성경·콘티·AI·편집·저장/복구 검사도 통과했다.

첫 전체 실행은 41/51 통과였으며 실패 원인을 수정한 뒤 54개 전체를 다시 실행했다. 기술 probe의 종료 대기를 임시 앱 process에 한정해 정리했고, upload 검사는 popup이 소비한 user activation과 파일 선택 동작을 분리했다. 기존 콘티 버튼 이름과 AI 첨부 prompt를 사용하는 테스트 mock을 현재 코드에 맞췄다. 기능 검사를 건너뛰거나 실패를 예상 통과로 바꾸지 않았다. 개발 startup의 의도적 초기화 실패 검사는 React preamble 오류를 출력하지만 해당 회복 경로의 기대 동작은 통과했다.

PDF 패널 합성 화면은 `test-results/output-resources-control.png`에 저장해 확인했다. source/hash 기준 HEAD는 `4dbdd7de94c72ff20ed385ec0e70e647d7c49a35`로 유지하며 커밋·푸시·공개 배포는 하지 않았다.

## 구현 범위와 설계 조정

- v3 작업 공간과 schema 2 전체 백업을 구현했다. 원곡·콘티·Presentation/Slide 형식은 유지한다. PDF 등록은 sandbox PDF.js helper에서 첫 페이지와 실제 페이지 수를 검사한 뒤 원본+자료를 기록한다.
- 웹은 별도 비영속 session과 하나의 native view다. 준비는 별도 직접 조작 창, 컨트롤은 캡처 미리보기이며 송출 중 조작은 명시적 잠금 해제로 제공한다.
- 준비 토큰·resource revision·generation이 전환을 검증한다. layers 전체 snapshot의 version은 WindowManager에서 계속 관리한다. 외부 자료 준비 뒤 hidden layers를 편집한 것만으로 준비를 취소하지 않으며, 명시적 슬라이드 실행·복귀·전체 중지·장비 resize는 준비를 무효화한다.
- PDF 캐시는 현재 실행 메모리에서 128MiB/20페이지로 제한하고 현재/다음/준비 페이지를 pin한다. 설계의 선택적 512MiB 디스크 캐시는 추가하지 않았다. 재시작 때 원본으로 렌더한다.
- 썸네일은 6페이지 단위로 요청하며 전체 문서를 선렌더하지 않는다. 모든 PDF worker 작업은 직렬 대기열과 15초 제한을 적용한다.
- 원격 파일 선택기는 빈 페이지에서 debugger Page domain을 준비한 뒤 실제 탐색 전에 intercept하며 탐색 후에도 다시 적용한다. 새 창·다운로드·권한·로컬 스킴 접근은 차단한다. 앱 CSP는 외부 웹 접속을 허용하지 않으며 PDF 읽기·frame은 내부 output: 프로토콜로 제공한다.
- PDF 파일 hash를 cache key에 포함해 재연결한 원본과 이전 render가 섞이지 않도록 한다. 준비 창에서 새 문서로 이동하면 generation과 준비 토큰을 무효화한다.
- 실제 단축키 전체 중지는 Main의 before-input-event에서 처리하여 native 브라우저·입력칸에서도 작동한다. PDF applied는 raster를 먼저 읽은 뒤 state 반영 version으로 확인한다.

## 개발 검사와 구분한 후속 수용

실제 외부 사이트의 로그인·DRM·팝업 인증, Windows 실행, 실장비 연결/분리·깜박임·음성 장치, 저사양 장비의 p95 성능 목표, 서명·공개 배포는 미실행이다. 개발 검사의 capture와 applied 응답은 프로젝터·스피커의 실물 표시 증거가 아니다.

## 패키지 UI 격리 확인

생성 macOS 패키지에 동일 UI 검사를 추가 시도했으나 `app.isPackaged`에서는 테스트 userData 설정을 사용하지 않아 8개 모두 준비 단계의 데이터 경로 assertion에서 중단했다. 해당 검사에서는 자료 등록·송출 절차를 수행하지 않았다. 실제 사용자 경로를 대상으로 검사를 계속하지 않았으며, 패키지 UI 수용은 완료로 기록하지 않는다. 패키지 생성과 내부 stdio 합성 호출 PASS 및 비패키지 Electron 최종 전체 55개 PASS와 구분한다.

해당 패키지 실행은 경로 assertion 전 startup에서 실제 데이터 폴더에 `workspace-v3.json`을 자동 생성했다. 원본 `workspace-v2.json`의 수정 시각은 이전 시각을 유지했고, 생성 v3는 v2에 schemaVersion 3과 빈 outputResources만 더한 객체와 정확히 같았다. 동시 변경이 없는지 재확인하고 생성 파일만 별도 임시 보존 폴더로 이동해 실제 데이터 폴더의 v1/v2 상태를 유지했다. 생성 파일은 `/tmp/propre-packaged-isolation-recovery-path.txt`가 가리키는 임시 폴더에 보존한다. 실제 사용자 경로의 파일을 검사에 사용하지 않도록 패키지 실행 옵션은 테스트에서 제거했다.

종료 추가 검사에서 컨트롤 창을 닫은 뒤 앱 종료 시 준비 창의 close 방지가 남을 수 있는 경로를 보완했다. before-quit에서 컨트롤 창이 없을 때도 외부 자료를 dispose하여 창·worker·native view를 정리한다.

최종 종료 경로 변경 후 전체 Electron 55개를 다시 실행하여 모두 통과했다. 이후 생산 번들을 사용해 디렉터리 패키지와 내부 stdio 합성 호출도 다시 확인했다.
